# AI Executive Architecture

The Phase 4A database model and evaluation pipeline behind the AI Executive workspace (`/[organizationSlug]/ai-executive`). For the rule/signal catalog, see `docs/AI_RULES_AND_SIGNALS.md`. For the approval/execution security model, see `docs/AI_APPROVAL_AND_ACTION_SECURITY.md`. For the local skill seam, see `docs/HOSPITALITY_PLUGIN_SKILL_ADAPTER.md`.

```text
Signals → Analysis → Recommendation → Approval → Action → Outcome → Memory
```

This phase ships every stage except long-term Memory (no learning loop yet — outcomes are recorded, not fed back into rule weighting).

---

## Why deterministic rules, not a model

Issue #18 scopes Phase 4A as "AI priorities generated from deterministic rules only" — the same constraint Phase 3's dashboard already operated under. There is no LLM call, no external AI service, and no non-deterministic behavior anywhere in the evaluation path: given the same facts and the same rule configuration, the same recommendations are produced every time. This is what "Deterministic mode" (the banner shown on every AI Executive page) means, and it's why every recommendation carries an `evidence` array traceable back to a real row, rather than free-text reasoning.

## Three-layer evaluation pipeline

Evaluation for one organization (`lib/ai/evaluate.ts::evaluateOrganization()`) runs in three distinct layers, each with a narrow, testable responsibility:

1. **Fact gathering** — `get_ai_evaluation_facts(p_organization_id, p_as_of, p_location_id)`, a single `SECURITY INVOKER`, `STABLE` RPC. Requires `ai.executive.read`. Issues a small, fixed number of aggregate queries (never N+1) and returns one `jsonb` object: `open_leads`, `reservations_tonight`, `recent_reservation_attrition`, `open_orders`, `latest_kpi_snapshot`, `today_kpi_snapshot`. Its lookback windows (30 days for open leads, 14 days for attrition, 3 days for open orders) are **generous performance bounds only** — they exist so the query stays bounded on a busy tenant, not because they encode a business threshold. Actual thresholds live one layer up, in rule config.
2. **Rule evaluation** — nine pure TypeScript functions (`lib/ai/rules/*.ts`), each a `RuleDefinition<TConfig>`: a Zod `configSchema`, a `defaultConfig`, and an `evaluate(context)` function that reads only the facts object and returns `{ signals, recommendations }`. Zero database access, fully unit-testable without a database at all — see `docs/AI_RULES_AND_SIGNALS.md` for the full catalog. `lib/ai/plugins/registry.ts::runLocalSkills()` runs alongside the built-in rules at this layer, on the same facts, contributing to the same combined output.
3. **Transactional apply** — `apply_ai_evaluation(p_organization_id, p_location_id, p_as_of, p_rule_version, p_intents)`, one `SECURITY DEFINER` RPC that takes the combined, Zod-validated output of every rule and skill for this run and applies it atomically: upserts signals, resolves stale signals within the exact scope this run targets, upserts recommendations (with reopening logic and executing-row immutability — see below), upserts evidence, expires anything obsolete within scope, and writes one audit event. Nothing about "did this run change anything" is ever computed by re-querying afterward from TypeScript; the function's return value (`signals_upserted`, `signals_resolved`, `recommendations_upserted`, `recommendations_deferred`, `recommendations_expired`, `approvals_expired`) is authoritative.

This split exists so the actual decision logic (layer 2) can be reviewed, tested, and reasoned about by reading plain TypeScript — no SQL, no database round trip — while both database-facing edges (layers 1 and 3) stay thin, auditable, and RLS/permission-checked independently of the rules that call them.

## Signals vs. recommendations vs. evidence

- **A signal** (`ai_signals`) is a continuously re-evaluated gauge, not a discrete event. The same `dedupe_key` always upserts the same row (`unique (organization_id, dedupe_key)`), flipping `status` between `active`/`resolved`/`suppressed` across evaluation runs rather than accumulating a new row every time a rule re-fires. "3 unanswered leads" today and "5 unanswered leads" tomorrow are the same signal row with different `facts`, not two rows. **`ai_signals.facts` has no finance.read redaction at all** (only `ai_recommendation_evidence` rows do, via RLS — see below) — every finance-sensitive rule (`revenue_target.v1`, `average_ticket.v1`, `stalled_orders.v1`) deliberately keeps raw dollar figures out of `facts` entirely (a qualitative flag like `{ belowTarget: true }`, or nothing at all) and puts the actual amount only in the recommendation's `isFinanceSensitive` evidence row. This is a Phase 4B fix — `docs/AI_RULES_AND_SIGNALS.md` documents it as a standing rule-authoring constraint, not just a one-time correction.
- **A recommendation** (`ai_recommendations`) is a discrete, actionable proposal: a title, an executive summary, a severity, a `priority_score`, and — if `requires_approval` — something concrete to approve. Recommendations use a *partial* unique index (`(organization_id, dedupe_key) where status in ('proposed','approved','executing')`), not a plain one: a recommendation can legitimately recur once its predecessor has resolved (`completed`/`failed`/`rejected`/`expired`/`dismissed`), but never duplicate while one is still open.
- **Evidence** (`ai_recommendation_evidence`) is the traceable justification behind a recommendation: one row per named metric, an `observed_value`, an optional `expected_value`, a human-readable `calculation_definition`, and an `is_finance_sensitive` flag (see redaction below). `unique(recommendation_id, metric_name)` lets a re-evaluation safely upsert evidence in place rather than delete-then-insert.

## Server-controlled payload hashing

`ai_recommendations.payload_hash` is a `generated always as (...) stored` column — Postgres itself computes it from `id | organization_id | recommended_action_type | action_schema_version | recommended_action_payload::text` via `digest(..., 'sha256')`, and no client (nor any application code) can ever supply or override it. This is the tamper-evident anchor for the entire approval→execution flow: `approve_ai_recommendation()` snapshots it into `ai_approvals.payload_hash_at_decision`, and `begin_ai_recommendation_execution()` refuses to start if the recommendation's *live* `payload_hash` no longer matches what was actually approved. Hashing the id and action type alongside the payload (not the payload alone) means a byte-identical payload can never be replayed against a different recommendation or action type. See `docs/AI_APPROVAL_AND_ACTION_SECURITY.md` for the full approval lifecycle.

## Reopening: what happens when an approved recommendation's facts change

A gap in the original design, found by tracing the pgTAP suite by hand rather than by a failing test run (no local Docker — see `docs/SUPABASE_OPERATIONS.md`): before this fix, there was no path back from `approved` once a recommendation's underlying facts changed. If a rule re-fired with a materially different payload for an already-`approved` recommendation, `apply_ai_evaluation()`'s upsert would silently overwrite the payload underneath a decision a human had already made — the approval would point at a payload that was never actually reviewed.

Fixed properly, not worked around: `apply_ai_evaluation()` now captures the pre-upsert `status`/`payload_hash`, compares them to the post-upsert `payload_hash`, and if an `approved` recommendation's payload actually changed, resets it to `proposed` and its approval back to `pending` (`version` incremented, `payload_hash_at_decision`/`decided_by_user_id`/`decided_at` cleared). Two new status-transition rows make this legal at the database level: `recommendation_status: approved → proposed` and `approval_status: approved → pending`. A previously-approved-but-now-stale recommendation must be reviewed again before it can execute — it is structurally impossible for a client to approve once and have that approval silently carry over new facts.

## Executing-recommendation immutability

Reopening (above) handles a payload change while a recommendation is `approved`, not yet executing — there, overwriting the payload and forcing re-approval is safe because nothing has acted on it yet. A recommendation that is currently `executing` is a different case entirely: a real `lib/operations/*` domain call may already be in flight against the *original* payload, so `apply_ai_evaluation()` must never let a re-evaluation change that row's `recommended_action_type`, `action_schema_version`, `recommended_action_payload`, `payload_hash`, evidence, or approval relationship out from under it. This was a real gap the Phase 4B security review found: the original upsert had no special case for `executing` at all.

Two options were considered for what to do with a materially-changed intent that arrives while its predecessor is executing: **(A)** defer it until the active execution finishes, or **(B)** create a separate, distinctly-keyed future recommendation immediately. **Chosen: (B).** `apply_ai_evaluation()` pre-checks the existing row's status by dedupe_key before upserting; if it's `executing`, the new intent is redirected to `<dedupe_key>:pending-reevaluation` instead — a completely independent recommendation (its own approval, its own evidence) that a human can review right away, rather than waiting on an execution that might fail, get recovered, or take a while. (A) was rejected because it would require either a background reconciliation job or a "replay this on next evaluation" mechanism — meaningfully more moving parts than a second row a human can just look at. The executing row itself is left **completely untouched**: the upsert's `ON CONFLICT` still names the same partial index (matching `executing` is required to name the correct arbiter), but by construction — the pre-check above always redirects before reaching it — that branch is never actually exercised against an executing row.

The active execution can still finalize normally against its original, untouched `execution_token` and `payload_hash` regardless of what happened to the deferred sibling. If a *third* evaluation arrives while **both** the original and its `:pending-reevaluation` counterpart are executing (a human approved and executed the deferred one too, before the third run), the intent is dropped for that one run rather than chaining a second suffix indefinitely — a deliberately accepted, rare edge case; the next evaluation run picks it back up once either execution resolves. `supabase/tests/ai_executive_concurrency.test.sql` and `tests/integration/ai-executive.test.ts` both cover the primary (non-nested) case end-to-end.

## Evaluation scope: organization-wide vs. location-specific

`apply_ai_evaluation(p_organization_id, p_location_id, ...)` must respect an exact scope contract, found broken by the Phase 4B review: the stale-signal-resolution and obsolete-recommendation-expiry passes used `p_location_id is null or location_id = p_location_id or location_id is null` — meaning a location-specific run (`p_location_id` set) would also resolve/expire organization-wide (`location_id is null`) rows, and vice versa. Fixed by replacing that predicate everywhere it gated a *mutation* with `location_id is not distinct from p_location_id` — exact, NULL-safe equality:

- **Organization-wide run** (`p_location_id is null`): only ever resolves/expires rows where `location_id is null`. It does not touch any specific location's signals or recommendations.
- **Location-specific run** (`p_location_id` set): only ever resolves/expires rows where `location_id` equals that exact value. It never touches organization-wide rows, and never touches a sibling location's rows.

This applies to stale-signal resolution, obsolete-recommendation expiry, and approval expiry (the latter via a join back to its recommendation's `location_id`, since `ai_approvals` itself carries no location). `get_ai_evaluation_facts()`'s *read* side is deliberately **not** symmetric with this: for entities that always belong to a real location (leads, reservations, orders), an organization-wide run intentionally reads every location's rows — the "intentionally manages every location" strategy the exact-scope contract explicitly allows for reads, since there's no meaningful "organization-wide lead" to restrict to. For `daily_kpi_snapshots`, which genuinely has both an org-wide rollup row (`location_id is null`) and per-location rows by design (Phase 3), an organization-wide run reads only the rollup — the "organization-wide records only" strategy — while a location-specific run reads only that exact location's snapshot, no fallback. `supabase/tests/ai_executive_concurrency.test.sql` proves the mutation-side fix directly with a second BOSSA location, an organization-wide signal/recommendation, and a location-specific one, confirming a location-A run leaves both the organization-wide and location-B rows completely unchanged.

## Rule scope and the evaluation orchestrator

The exact-scope contract above only means something if the right rules actually run at the right granularity — the Phase 4C review found that gap too: `get_ai_evaluation_facts(p_location_id = null)` reads every location's leads/reservations/orders, several rules emit an entity's own `location_id` regardless of what scope the run declared, and nothing stopped a rule (or a bug in whatever calls `apply_ai_evaluation()`) from writing a location-tagged row during a nominally "organization-wide" run. Two structural fixes close it:

**Explicit rule scope metadata.** Every `RuleDefinition` (`lib/ai/rules/types.ts`) and every `SkillManifest` (`lib/ai/plugins/types.ts`) now declares a `scope: "organization" | "location" | "both"`:

- **`location`** (`unanswered_leads.v1`, `aging_leads.v1`, `reservation_capacity.v1`, `reservation_attrition.v1`, `stalled_orders.v1`, `delayed_orders.v1`, and the `vipReservationConciergeSkill` reference skill) — genuinely per-location operational conditions. These only ever run as part of a location-scoped evaluation.
- **`both`** (`revenue_target.v1`, `average_ticket.v1`, `kpi_staleness.v1`) — meaningful at both the organization-wide rollup level and each individual location's level, matching `daily_kpi_snapshots`'s own dual nature (a real org-wide rollup row alongside real per-location rows). These run in every location-scoped evaluation *and* the one organization-scoped evaluation.
- **`organization`** — reserved for a rule that is only ever meaningful org-wide. None of the current catalog needs it, but the type exists so a future rule can declare it precisely rather than defaulting to `both` out of convenience.

`evaluateOrganization(supabase, organizationId, { locationId })` — the single-scope primitive — now filters `RULE_REGISTRY` and `SKILL_REGISTRY` by `ruleAppliesToScope(rule.scope, locationId)` before evaluating anything: called with `locationId: null` it only ever runs `organization`/`both`-scoped rules; called with a specific location it only ever runs `location`/`both`-scoped rules. Calling it bare, with no location, is no longer "the org-wide evaluation" in the way it used to be — it now only covers a third of the catalog.

**The orchestrator.** `lib/ai/orchestrate.ts::evaluateOrganizationAcrossLocations()` is the primary entry point real usage should call instead (`scripts/evaluate-ai-executive.ts` does): it fetches the organization's currently active locations fresh from the `locations` table every time, calls `evaluateOrganization()` once per location, then once more for the organization-wide scope. Adding a third location requires no code change here — the next run simply discovers it. Each call still goes through `apply_ai_evaluation()`'s own **mixed-scope validation**, added as a second, independent layer of defense: every signal/recommendation intent's own `location_id`, if the rule states one at all (including an explicit `null`), must exactly equal the run's `p_location_id` — omitting the field entirely defers to the run's own scope (the same `coalesce()` every rule already relies on), but stating a *different* location, or stating `null` during a location-scoped run, is rejected outright with `VALIDATION_FAILED`, before a single row is written. A rule author's mistake, or a bug in the orchestrator's wiring, can never silently create a location-specific row during an organization-wide run, or a cross-location row during a location-specific run — the database itself refuses it.

`lib/ai/evaluate.ts::loadRuleConfigs()`'s rule-config resolution was already exact (a location-specific override only applies to its own location; an org-wide override serves only as the fallback when no location-specific one exists) and needed no change — `tests/integration/ai-executive.test.ts` verifies both rows remain independently resolvable. `supabase/tests/ai_executive_orchestration.test.sql` proves the validation directly in both directions (organization run rejects a location-tagged intent, location run rejects a wrong-location or explicit-null intent), plus a location-scoped signal correctly resolving on a later empty run for that exact location; `tests/integration/ai-executive.test.ts` proves the orchestrator discovers a newly-added location with no code change.

## Polymorphic evidence and signal source references

`ai_signals.source_entity_type`/`source_entity_id` and `ai_recommendation_evidence.source_entity_type`/`source_entity_id` can point at any of five domain tables (`lead`, `reservation`, `order`, `order_item`, `daily_kpi_snapshot`) — no single foreign key can express "one of five possible tables." `validate_ai_source_entity_reference()` (one generic `BEFORE INSERT/UPDATE` trigger function, attached to both tables) reads the row generically via `to_jsonb(new)`, looks up the referenced row in whichever table `source_entity_type` names, and checks both existence and organization match, and — for **all five** supported types, including `lead` (its own `location_id`) and `order_item` (resolved via a join to its parent `order`'s `location_id`, since `order_items` carries no `location_id` of its own) — location match where the referencing row has a location context. (Phase 4B fix: `lead` and `order_item` previously never populated their source location at all, so the mismatch branch could never fire for either type — only `reservation`, `order`, and `daily_kpi_snapshot` were actually checked.) An organization-wide recommendation (`location_id is null`) has no location context to mismatch against at all, so it may reference evidence from any location, by design — this is tested explicitly, not just implied. This is the same "schema-level impossibility" property Phase 3's composite FKs give single-table references, extended to a polymorphic one via a trigger instead of a constraint.

## Database model summary

Seven tables, all `organization_id`-scoped, migrations `20260723000001`–`20260723000009` (Phase 4A) plus `20260724000001`–`20260724000003` (Phase 4B: execution-claim columns, location-validation fix, scope/immutability fix):

| Table | Role | Directly writable by `authenticated`? |
| --- | --- | --- |
| `ai_rule_configs` | Tenant-scoped threshold overrides | Yes — the one table with direct INSERT/UPDATE grants |
| `ai_signals` | Continuously re-evaluated gauges | No — only via `apply_ai_evaluation()` |
| `ai_recommendations` | Discrete actionable proposals; also carries the execution claim (`execution_token`, `executing_at`, `execution_attempt_number`) | No — only via the approval/execution/recovery functions below |
| `ai_recommendation_evidence` | Traceable per-metric justification | No — only via `apply_ai_evaluation()` |
| `ai_approvals` | One decision row per recommendation | No — only via `approve_ai_recommendation()`/`reject_ai_recommendation()` |
| `ai_action_attempts` | Append-only execution history; also carries the `execution_token`/`execution_attempt_number` that produced each row | No — only via `record_ai_action_attempt()` |
| `ai_outcomes` | Measured result of an executed action | No — only via `record_ai_outcome()` |

Full column-level detail lives in the migrations themselves (`supabase/migrations/20260723000001_ai_tables.sql`, `20260724000001_ai_execution_concurrency.sql`); this table is a map of *who can write what*, not a schema reference. See `docs/AI_APPROVAL_AND_ACTION_SECURITY.md` for the execution-claim lifecycle, duplicate-success index, and crash-recovery design.

## Dashboard integration

`lib/dashboard/supabase-provider.ts` sources `aiPriorities` (top 5 open recommendations by `priority_score`), `liveAlerts` (active warning/critical signals), and `approvalQueue` (pending approvals joined in-memory to their recommendations) from these tables — replacing the ad-hoc derivations Phase 3 computed directly from operational data. `DashboardData`'s shape is unchanged; only where these three fields come from changed.

## What Phase 4A deliberately does not build

- No scheduler. `scripts/evaluate-ai-executive.ts` (`npm run ai:evaluate -- --org=<slug> --as-of=<iso>`) is the same manual-CLI-invocation pattern Phase 3's `generate-kpi-snapshots.ts` established — no Vercel Cron or Supabase scheduled job is enabled.
- No memory/learning loop. Outcomes are recorded (`ai_outcomes`) for human review and future analysis, but nothing currently feeds them back into rule weighting or priority scoring.
- No non-deterministic or model-backed recommendation source. The local skill seam (`docs/HOSPITALITY_PLUGIN_SKILL_ADAPTER.md`) is inert and fixture-based in this phase — a real `hospitality-os-plugin` integration is future work, not part of Phase 4A.
